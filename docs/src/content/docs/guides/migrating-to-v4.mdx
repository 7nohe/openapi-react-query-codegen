---
title: Migrating to v4
description: Migration guide from v3 to v4 of OpenAPI React Query Codegen.
---

v4 replaces `@hey-api/openapi-ts` with a client generator that ships inside this package. The generated **hooks are unchanged** — same names, same signatures, same query keys — so for most projects migrating means updating the package, regenerating, and checking the handful of differences below.

## TL;DR

1. Update the package and regenerate:

   ```bash
   npm install -D @7nohe/openapi-react-query-codegen@^4
   npx openapi-rq -i ./petstore.yaml
   ```

2. If you pass `-c @hey-api/client-fetch` or `-c @hey-api/client-axios`, both still work. Prefer the new spellings `-c fetch` and `-c axios`.
3. Delete the stale `client/` and `core/` folders from `openapi/requests` (the easiest way is to remove the whole `openapi` folder before regenerating).
4. If you used `--useDateType`, `--noSchemas` or `--schemaType`, see [removed options](#removed-options).
5. Everything else is compatible — you are done.

## What stays the same

- Every generated hook, prefetch/`ensureQueryData` function, `queryOptions` factory, key constant and key function keeps its v3 name and signature. For the same specification the generated `openapi/queries` files differ from v3 only in the order of import specifiers.
- `client` is still exported from `openapi/requests/client.gen` (and from the `services.gen` compatibility shim) with `setConfig()` and `interceptors`.
- SDK functions keep the `{ data, error, request, response }` result and throw the error when `throwOnError` is set. The hooks always set it, so failed requests reject (as in v3).
- `--format`, `--lint`, `--enums`, `--noOperationId`, `--pageParam`, `--nextPageParam`, `--initialPageParam` and `--omitInitialPageParam` behave as before.

## What changed

### `openapi/requests`

| v3 | v4 |
| --- | --- |
| `client/`, `core/` (Hey API runtime) | `runtime.gen.ts` (one file) |
| `client.gen.ts`, `sdk.gen.ts`, `types.gen.ts`, `services.gen.ts`, `index.ts` | same names |
| `schemas.gen.ts` (JSON schemas) | not generated |

Anything that imported from `openapi/requests/client` or `openapi/requests/core` needs to import from `openapi/requests/runtime.gen` instead (for example the `Config` and `Options` types).

### The HTTP runtimes

The runtimes are small, dependency-free TypeScript files generated into your project (`axios` aside). They cover what the hooks and typical applications use:

- `baseUrl` (`baseURL` for axios), `headers`, `throwOnError`, `signal` and any other `fetch` option
- request, response and error `interceptors` (fetch) or `client.instance.interceptors` (axios)
- `auth` for operations with `security` (bearer, basic and API keys in header, query or cookie), including schemes an operation requires together
- `querySerializer`, `pathSerializer` and `bodySerializer`, with OpenAPI `style`/`explode` honoured per query and path parameter
- JSON, `multipart/form-data`, `application/x-www-form-urlencoded`, text and binary request bodies; JSON, text, blob, form data and stream responses via `parseAs`

Three behaviours differ from v3, each to follow the specification:

- A query parameter whose schema is a `$ref` to an object and that has no `style` is sent in the OpenAPI default, `form` with `explode` (`role=admin`). v3 did this for inline object schemas but sent `$ref`s as `filter[role]=admin`. Specify `style: deepObject` to keep that form.
- Path parameters with `style: label` or `style: matrix`, or an exploded object, are serialized as declared. v3 ignored both settings.
- With `-c axios`, a JSON request body that is a string is always sent as a JSON string. v3 sent a string that happened to parse as JSON, such as `"true"`, as that JSON value.

Not carried over from the Hey API clients: server-sent events, `responseValidator`/`responseTransformer`, and the `runtimeConfigPath` option. If you relied on them, keep calling those parts of your API through your own code.

### Specification support

OpenAPI 3.0 and 3.1 are supported, including external `$ref`s to files and URLs. Swagger/OpenAPI 2.0 documents are rejected with an explicit error — convert them to OpenAPI 3 first.

### Naming

- Operations without an `operationId` are named after the method and path (`getPetsById`), as before.
- A name that would collide with a schema or another operation's type gets a number appended on its own, instead of producing duplicate identifiers or renaming the whole operation. For example, when the specification has a `ListRunsResponse` schema and an operation `listRuns`, the schema keeps its name, `ListRunsData` / `ListRunsResponses` / `ListRunsErrors` keep theirs, and only the alias becomes `ListRunsResponse2`. The hooks keep their names.
- Schema names are converted to PascalCase as in v3 (`account_annual_revenue` → `AccountAnnualRevenue`, `FineTuneDPOHyperparameters` → `FineTuneDpoHyperparameters`).
- A digit-leading `operationId` such as `123numericLead` yields the function `_123NumericLead` and the types `_123NumericLeadData` / `_123NumericLeadError` (v3 dropped the digits from the types only).

- Some names are taken by what generated code uses, and get a suffix where v3 failed to compile: schemas such as `Options`, `Array`, `Promise`, `Omit` or `QueryClient` become `Options2`, `Array2` and so on, and operations such as `client`, `options`, `queryClient` or `useQuery` become `client_`, `options_`, `queryClient_` and `useQuery_` (their hooks are `useClient_`, …). Schemas named `Blob` and `File` keep their names, and binary fields refer to `globalThis.Blob` and `globalThis.File`.

### Types that are no longer generated

v3 emitted a few helper types that no hook uses. They are gone in v4; if your code imports one, declare it yourself from the schema:

- types for `components.parameters` (for example `Page` for a `Page` parameter) and for webhooks (`Webhooks`, `…WebhookRequest`)
- anonymous helper names such as `Pet2` or `UserArray` for inline schemas
- `*Writable` aliases of schemas that have no `readOnly`/`writeOnly` property. A real request-side variant (`PetWritable`, without the `readOnly` properties) is still generated, and the type of a `readOnly` property is now `readonly` in response types.

Two typing differences to be aware of: a fixed-length array (`minItems` equal to `maxItems`) is a tuple, as before, and when `prefixItems` is followed by `items` the remaining elements are typed as `...Array<T>` rather than one extra tuple member. `oneOf`/`anyOf` members with a `discriminator` are narrowed by the discriminator value unless the member already pins the property to literals. In OpenAPI 3.1, keywords next to a `$ref` (`properties`, `required`, …) now apply together with the reference, while OpenAPI 3.0 keeps ignoring them as the specification says.

### Performance

Large specifications generate much faster, mostly because the hook files now import only the models they use: the 4 MB OpenAI specification (388 operations) takes about 5 seconds instead of about 30.

## Removed options

These options were thin pass-throughs to Hey API plugins and are not implemented in v4. Passing them now fails with an "unknown option" error rather than being ignored.

| Option | What to do |
| --- | --- |
| `--useDateType` | Date-typed properties and the response transformer are not generated. `date`/`date-time` values stay `string`. Convert at the edge of your application or in an interceptor. |
| `--noSchemas`, `--schemaType` | JSON schema objects (`schemas.gen.ts`) are no longer generated, so there is nothing to switch off. |

## Dependency changes

- `@hey-api/openapi-ts` is no longer a dependency, so its (FSL) license no longer applies to your install.
- `yaml` (exact-pinned, no dependencies of its own) was added to parse YAML specifications.
- Peer dependencies are unchanged. `axios` is needed in your project only with `-c axios`.
